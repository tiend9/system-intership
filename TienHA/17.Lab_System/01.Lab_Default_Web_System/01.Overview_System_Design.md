# SYSTEM DESIGN

## I. Tổng quan System Design

### 1. System Design Là gì?

- System Design là quá trình thiết kế các hệ thống quy mô lớn,
đáng tin cậy, có khả năng mở rộng và hiệu quả để giải quyết
các vấn đề thực tế trong thế giới thực.

### 2. Tại sao cần System Design?

- Giúp xây dựng các hệ thống có khả năng mở rộng.
- Xử lý lưu lượng truy cập cao và dữ liệu lớn.
- Cải thiện tính sẵn sàng, độ tin cậy và hiệu suất.
- Giúp hệ thống chịu lỗi và dễ dàng khắc phục sự cố.

### 3. Kiến trúc cấp cao điển hình

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_1.png)

### 4. Yêu cầu qua Internet như thế nào ?

Khi bạn nhập một URL vào trình duyệt và nhấn `Enter`, rất nhiều
điều xảy ra phía sau hậu trường.

Các thành phần chính liên quan gồm:

1. **DNS (Hệ thống tên miền)** - Chuyển đổi tên miền thành địa chỉ IP.
2. **Bộ cân bằng tải (Load Balancer)** - Phân phối các yêu cầu đến nhiều máy chủ.
3. **Máy chủ ứng dụng (Application Server)** - Xừ lý yêu cầu và chứa logic nghiệp vụ.
4. **Redis (Bộ nhớ đệm)** - Lưu trữ dữ liệu được truy cập thường xuyên để phản hồi nhanh hơn.
5. **Cơ sở dữ liệu (Database)** - Lưu trữ dữ liệu lâu dài.

Hãy cùng xem toàn bộ luồng hoạt động

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_2.png)

Các bước trong luồng hoạt động :

1. Người dùng nhập URL vào trình duyệt và nhấn Enter.
2. Trình duyệt gửi yêu cầu đến máy chủ DNS để phân giải tên miền.
3. DNS trả về địa chi IP của máy chủ (hoặc của Bộ cân bằng tải).
4. Yêu cầu được gửi đến Bộ cân bằng tài.
5. Bộ cân bằng tải chọn một Máy chủ ứng dụng và chuyển tiếp yêu cầu.
6. Máy chủ ứng dụng kiểm tra Bộ nhớ đệm (Redis) hoặc đọc/ghi dữ liệu từ Cơ sở dữ liệu.
7. Dữ liệu được trả về Máy chủ ứng dụng, sau đó về Bộ cân bằng tải,
và cuối cùng đến Người dùng.

## II. Máy chủ ứng dụng (Application Server)

### 1. Máy chủ ứng dụng là gì?

Máy chủ ứng dụng xử lý yêu cầu, chứa logic nghiệp vụ của ứng dụng
và tương tác với Redis (Cache) / Cơ sở dừ liệu (Database)
để lấy hoặc lưu trữ dữ liệu.

Trách nhiệm :

- Xử lý các yêu cầu từ phía client.
- Thực thi logic nghiệp vụ.
- Tương tác với Redis (Cache) để truy cập nhanh hơn.
- Đọc từ / Ghi vào Cơ sở dữ liệu nếu không có trong cache.
- Trả kết quả trở lại Bộ cân bằng tải.

### 2. Máy chủ ứng dụng hoạt động như nào ?

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_3.png)

### 3. Luồng hoạt động chi tiết ?

1. Bộ cân bằng tải (Load Balancer) chuyển tiếp yêu cầu đến một trong các Máy chủ ứng dụng.

2. Máy chủ ứng dụng kiểm tra Redis (Cache) để tìm dữ liệu cần thiết
• Nếu tìm thấy trong cache (Hit) → Sử dụng dữ liệu từ cache.
• Nếu không tim thấy (Miss) → Lấy dữ liệu từ Cơ sở dữ liệu.

3. Nếu dữ liệu được lấy từ Cơ sở dừ liệu, lưu vào Redis để phục vụ các yêu cầu sau.

4. Máy chủ ứng dụng xử lý yêu cầu và tạo kết quả phản hồi.

5. Gửi kết quả phản hồi trở lại Bộ cân bằng tải. Bộ cân bằng tải trả kết quả lại cho người dùng.

## III. Cache

### 1. Redis là gì?

Redis là một kho dữ liệu trong bộ nhớ (in-memory data structure store), được sử dụng làm cache, message broker và cơ sở dừ liệu.
Nó lưu trữ dữ liệu theo dạng key-value và có tốc độ rất nhanh.

### 2. Chức năng Redis (Cache)?

- Lưu trữ dữ liệu được truy cập thường xuyên trong bộ nhớ.
- Giảm tải cho Cơ sở dữ liệu (Database).
- Tăng tốc độ phản hồi.
- Hỗ trợ nhiều cấu trúc dừ liệu (String, Hash, List, Set, Sorted Set, ....)
- Có thể dùng cho pub/sub(Nhắn tin), lưu trữ phiên (session store),
giới hạn tốc độ (rate limiting), bảng xếp hạng (leaderboards), v.v.

### 3. Redis hoạt động như nào ?

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_4.png)

- Ứng dụng trước tiên kiểm tra Redis để tim dừ liệu.
- Nếu tim thấy (Hit) → trả dừ liệu
về ứng dụng.
- Nếu không tìm thấy (Miss) → lấy dừ liệu từ Cơ sở dừ liệu.
- Lưu dữ Liệu vào Redis để phục vụ các yêu cầu sau và trả kết quả về ứng dụng.

Các cấu trúc dừ liệu phổ biến trong Redis

- String      -> key: value
- Hash        -> key: field: value
- List        -> key: [a,b,c]
- Set         -> key: [a,b,c]
- Sorted Set  -> key: [a,b,c]

### 4. Chi tiết về các khái niệm trong Cache

1. **Cache Hit** (Tìm thấy trong cache)

- Khi dữ liệu yêu cầu được tìm thấy trong Redis cache.

→ Trả về kết quả nhanh, không cần truy cập Co sở dữ liệu.

2. **Cache Miss** (Không tim thấy trong cache)

- Khi dữ liệu yêu câu không được tìm thấy trong Redis cache.

→ Dữ liệu sẽ được lấy từ Cơ sở dữ liệu và lưu vào Redis
để phục vụ các yêu cầu sau.

3. **TTL** (Time To Live - Thời gian sống)

- Thời gian hết hạn của một khóa trong Redis.
- Sau khi TTL hết hạn, khóa sẽ bị xóa tự động.
- Giúp giữ dữ liệu luôn mới và tiết kiệm bộ nhớ.
Cú pháp: `SET khóa giá _trị EX 60` → (hết hạn sau 60 giây)

4. **Eviction** (Chính sách loại bỏ)

- Khi bộ nhớ Redis đầy và cần lưu dữ liệu mới.
- Redis sẽ xóa một số khóa cũ dựa trên chính sách loại bỏ.

Các chính sách loại bỏ phổ biến :

1. **noeviction** → không xóa gì cả, chỉ trả về Lỗi.

2. **allkeys -Lru** → xóa khóa ít được sử dụng lâu nhất.

3. **allkeys-random** → xóa ngẫu nhiên một khóa.

4. **volatile -Lru** → xóa khóa có TTL, ít được sử dụng lâu nhất.

5. **volatile -ttl** → xóa khóa có TTL ngắn nhất.

## IV. Database Scalling (Mở rộng Database)

1. Mở rộng theo chiều dọc (Scale Up)

- Tăng sức mạnh của máy chủ hiện có.
- Thêm nhiều CPU, RAM, SSD, v.v.
- Dễ dàng nhưng có giới hạn.

2. Mở rộng theo chiều ngang (Scale Out)

- Thêm nhiều máy chủ hơn để xử lý tải
- Phân phối tải giữa nhiều máy chủ.
- Phức tạp hơn nhưng khả năng mở rộng cao.

3. Đọc từ bản sao (Read Replica)

- Sao chép Cơ sở dữ liệu chính.
- Dùng cho các thao tác đọc.
- Giúp giảm tải cho Cơ sở dữ liệu ghi (Write DB).

4. Cơ sở dữ liệu ghi (Primary)

- Cơ sở dữ liệu chính nơi tất cả thao tác ghi được thực hiện (Insert, Update, Delete).
- Đảm bảo tính nhất quán dữ liệu.

### 1. Sơ đồ kiến trúc

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_6.png)

### 2. Cách hoạt động

Cách hoạt động:

1. Client gửi yêu cầu.
2. Bộ cân bằng tải (Load Balancer) chuyển tiếp yêu cầu ghi đến Cơ sở dữ liệu ghi (Primary)
3. Cơ sở dữ liệu chính xử lý các thao tác ghi và sao chép dừ liệu đến các bản sao đọc.
4. Bô cân bằng tải chuyển tiếp các yêu cầu đọc đến các bản sao đọc (Read Replicas).

## V. Cổng API

**API Gateway** là một điểm truy cập duy nhất cho tất cả các yêu cầu từ cient.

Nó nằm giữa client và nhiều dịch vụ backend. Có nhiệm vụ:

1. **Xác thực (Authentication)**

- Xác thực người dùng / client.
- Kiểm tra token, khóa API hoặc thông tin đăng nhập.
- Nếu hợp lệ → chuyển tiếp yêu cầu.
- Nếu không hợp Lệ → trả về Lỗi.

2. **Định tuyến (Routing)**

- Xác định dịch vụ nào sẽ xử lý yêu cầu.
- Dựa trên đường dẫn (path), tiêu đề (header) hoặc tham số.
- Chuyển tiếp yêu cầu đến đúng dịch vụ.

3. **Giới hạn tốc độ (Rate Limiting)**

- Giới hạn số lượng yêu cầu từ một dient.
- Ngăn chặn lạm dụng và bảo vệ dịch vụ.
- Vi dụ: 100 yêu cầu / phút / mỗi người dùng

4. **Ghi log (Logging)**

- Ghi lại tất cả các yêu cầu và phản hồi.
- Hỗ trợ giám sát và gỡ lỗi.
- Lưu trữ metadata như thời gian, mã trạng thái, độ trễ, v.v.

### 1. Sơ đồ kiến trúc API Gateway

Cách hoạt động (Luồng xử lý)

### 3. Một số cơ chế Load balancing phổ biến

**Load balancing** có thể chia theo 2 khía cạnh: thuật toán phân phối traffic và tầng mạng hoạt động (L4 vs L7). Dưới đây là các cơ chế phổ biến nhất.

**Round Robin**: Phân phối request lần lượt, tuần tự qua từng server theo vòng tròn.

- Ưu điểm: đơn giản, dễ implement.
- Nhược điểm: không quan tâm tải thực tế của từng server — nếu server yếu hơn vẫn nhận số request bằng server mạnh.

**Weighted Round Robin**: Giống Round Robin nhưng mỗi server có 1 trọng số (weight) dựa trên năng lực xử lý. Server có weight cao hơn nhận nhiều request hơn.

- VD: Server A (weight=3), Server B (weight=1) → A nhận gấp 3 lần request so với B.

**Least Connections**: Route request đến server đang có ít connection đang xử lý nhất.Phù hợp khi các request có thời gian xử lý không đồng đều (long-lived connection, WebSocket...).

**Weighted Least Connections**: Kết hợp Least Connections + trọng số theo năng lực server.

**IP Hash**:Dùng hash từ IP của client để quyết định server nào xử lý.
Đảm bảo cùng 1 client luôn vào cùng 1 server (session persistence/sticky session) mà không cần lưu state ở LB.

- Nhược điểm: nếu 1 IP tạo ra traffic lớn bất thường, dễ gây mất cân bằng.

**Consistent Hashing**: Biến thể nâng cao của Hash-based, dùng nhiều trong hệ thống cache/database phân tán (VD: Redis Cluster, CDN, Memcached).

- Khi thêm/bớt server, chỉ 1 phần nhỏ dữ liệu/traffic bị re-route lại (thay vì toàn bộ như hash thường) — giảm thiểu "cache stampede" khi scale.

**Least Response Time**:Route đến server có thời gian phản hồi thấp nhất (kết hợp cả số connection và latency đo được).

- Thông minh hơn Least Connections vì tính đến hiệu năng thực tế theo thời gian thực.

**Sticky Session (Session Persistence)**:Không hẳn là thuật toán riêng mà là cơ chế bổ sung — đảm bảo user luôn được route về cùng 1 server trong suốt phiên làm việc.

- Cách implement: dựa vào cookie, IP Hash, hoặc session ID.
- Cần thiết khi server lưu session state cục bộ (không dùng shared session store như Redis).

## VII. Hàng đợi tin nhắn (Kafka/RabbitMq)

Hàng đợi tin nhắn được sử dụng để giao tiếp không đồng bộ giữa các dịch vụ / ứng dụng.

1. **Producer (Nhà sản xuất)**

- Tạo / gửi các tin nhắn vào hàng đợi (topic).
- Không cần chờ phản hồi từ consumer.

2. **Queue (Broker)**

- Lưu trữ tin nhắn cho đến khi consumer đọc chúng.
- Đảm bảo việc giao tin nhắn.

3. **Consumer (Người tiêu thụ)**

- Đọc / tiêu thụ tin nhắn từ hàng đợi.
- Xử lý tin nhắn.

4. **Cơ chế thử lại (Retry Mechanism)**

- Nếu xử lý thất bại, tin nhắn có thể được thử lại.
- Ngăn ngừa mất dữ liệu.

5. **Hàng đợi thư chết (Dead Letter Queue - DLQ)**

- Những tin nhắn thất bại ngay cả sau nhiều lần thử sẽ được chuyển vào DLQ.
- Hỗ trợ việc gỡ lỗi và xử lý thủ công.

### 1. Sơ đồ kiến trúc hoạt động

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_10.png)

Luồng xử lý (Flow)

1. Producer gửi tin nhắn lên Broker.
2. Broker giao tin nhắn cho Consumer.
3. Consumer xử lý tin nhắn (có thể ghi vào Database).
4. Nếu xử lý thất bại, tin nhắn được đưa vào Retry Queue để thử lại.
5. Nếu vẫn thất bại sau N lần thử, tin nhắn được chuyển vào Dead Letter Queue (DLQ).

### 2. Các khái niệm mở rộng

1. **Phân vùng (Kafka)**

- Topic được chia thành nhiều phân vùng.
- Tin nhắn trong mỗi phân vùng được sắp xếp.
- Phân vùng cho phép xử lý song song
bởi các consumer.
- Mỗi phân vùng có offset riêng.

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_11.png)

2. **Nhóm consumer**

- Các consumer làm việc trong một nhóm để
tiêu thụ tin nhắn.
- Mỗi phân vùng chỉ được tiêu thụ bởi
một consumer trong cùng nhóm.
- Điều này cho phép tiêu thụ song song.

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_12.png)

3. **Offset (Độ lệch)**

- Offset là ID duy nhất của mỗi tin nhắn
trong một phân vùng.
- Consumer cam kết (commit) offset sau
khi xử lý.
- Khi khởi động lại, consumer đọc từ
offset đã cam kết cuối cùng.

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_13.png)

4. **Chính sách lưu giữ (Retention Policy)**

- Xác định tin nhắn được giữ lại bao lâu.
- Lưu giữ theo thời gian (ví dụ: 7 ngày).
- Lưu giữ theo kích thước (ví dụ: 10 GB).
- Sau thời gian lưu giữ, tin nhắn cũ bị xóa.

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_14.png)

5. **Bảo đảm thứ tự (Ordering Guarantee)**

- Tin nhắn được sắp xếp trong một phân vùng.
- Không có đảm bảo thứ tự trên các phân vùng.
- Sử dụng một phân vùng nếu cần thứ tự nghiêm ngặt.

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_15.png)

6. **Xử lý đúng một lần (Exactly-Once Processing - Kafka)**

- Đảm bảo một tin nhắn được xử lý đúng một lần.
- Yêu cầu producer không có trạng thái (idempotent) + giao dịch (transaction).

- Ngăn chặn bản sao trùng lặp ngay cả khi có lỗi.

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_16.png)

## VIII. Mạng phân phối nội dung

CDN là một mạng lưới phân tán gồm các máy chủ, cung cấp nội dung tĩnh cho người dùng từ vị trí gần họ nhất.

1. **Nội dung tĩnh**

- CDN phù hợp nhất cho nội dung tĩnh.
- Ví dụ: hình ảnh, CSS, JS, video,
PDF, phông chữ, v.v.
- Nội dung động thường sẽ được gửi
từ máy chủ gốc.

2. **Máy chủ biên (Edge Servers)**

- CDN có các máy chủ biên (PoP)
ở nhiều khu vực.
- Các máy chủ biên này nằm gần
người dùng hơn.
- Nội dung được lưu ở biên để
giao nhanh hơn.

3. **Bộ nhớ đệm (Cache)**

- Nội dung được lưu trong bộ nhớ
đệm tại máy chủ biên.

- Nếu nội dung được yêu cầu có trong
cache → cache hit (nhanh).

- Nếu không → cache miss →
lấy từ máy chủ gốc.

4. **Độ trễ (Latency)**

- Phục vụ nội dung từ máy chủ gần
nhất giúp giảm khoảng cách mạng.
- Độ trễ thấp → trải nghiệm người
dùng tốt hơn.
- Rất quan trọng cho các ứng dụng
toàn cầu.

5. **Lợi ích (Benefits)**

- Giao nội dung nhanh hơn.
- Giảm tải cho máy chủ gốc.
- Cải thiện tính sẵn sàng và độ tin cậy.
- Trải nghiệm người dùng tốt hơn.
- Tiết kiệm chi phí bãng thông.

### 1. Kiến trúc CDN

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_17.png)

Luồng hoạt động qua CDN:

1. Người dùng yêu cầu nội dung tĩnh (ví dụ: hình ảnh, tệp JS).
2. DNS định tuyến yêu cầu đến máy chủ biên CDN gần nhất.
3. Máy chủ biên kiểm tra cache.
    a. Nếu cache hit → trả nội dung từ biên (nhanh).
    b. Nếu cache miss → máy chủ biên lấy từ máy chủ gốc.
4. Máy chủ biên lưu nội dung vào cache.
5. Nội dung được trả về cho người dùng.

### 2. Các thành phần CDN

## X. Phân chia CSDL

Sharding là kỹ thuật phân vùng dữ liệu theo chiều ngang trên nhiều cơ sở dữ liệu (shard) khác nhau để cải thiện khả năng mở rộng và hiệu suất.

### 1. Tại sao cần Sharding?

- Xử lý lượng dữ liệu lớn.
- Phân tán tài đọc / ghi.
- Tránh điểm nghẽn của một cơ sở dữ liệu duy nhất.
- Cải thiện tính sẵn sàng.

### 2. Các thuật ngữ quan trọng

- **Shard**: Một phiên bản của cơ sở dữ liệu.

- **Khóa phân chia (Sharding Key)**: Cột được sử dụng để quyết định shard nào sẽ lưu trữ dữ liệu.

- **Bộ định tuyến / Trung gian (Router / Middleware)**: Quyết định shard phù hợp cho một truy vấn.

### 3. Sharding hoạt động như nào ?

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_20.png)

### 4. Các chiến lược Sharding phổ biến

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_21.png)

### 5. Ví dụ (Sharding theo hàm băm)

Khóa phân chia: `user_id`

Số shard: `3`

- `user_id` = `101` → `hash(101) % 3` = `2` → Shard `2`
- `user_id` = `102` → `hash(102) % 3` = `0` → Shard `0`
- `user_id` = `103` → `hash(103) % 3` = `1` → Shard `1`
- `user_id` = `104` → `hash(104) % 3` = `2` → Shard `2`

### 6. Nhược điểm sharding

- Việc JOIN giữa các shard khó khăn
- Re-sharding (tái phân chia) phức tạp
- Các giao dịch shard khó xử lí
- Phân phối dữ liệu không đều
- Chi phí vận hành cao hơn

## XI. Rate Limit

### 1. Khái niệm

**Rate Limiting** là kỹ thuật giới hạn số lượng request/hành động mà một client (user, IP, API key...) được phép thực hiện trong một khoảng thời gian nhất định.

### 2. Vì sao cần Rate Limit?

- Chống lạm dụng/spam: ngăn 1 user gọi API quá nhiều lần
- Chống DDoS/brute-force: giới hạn số lần thử đăng nhập, request login
- Bảo vệ hệ thống backend: tránh quá tải database, service downstream
- Fair usage: đảm bảo tài nguyên chia đều cho nhiều client
- Kiểm soát chi phí: giới hạn gọi API bên thứ 3 (tính phí theo request)

### 3. Thuật toán sử dụng trên Rate Limit

- **Fixed Window Counter**: Chia thời gian thành khung cố định.(VD: Phút 1 được bao request,Phút 2 được bao request, Phút 3 bao reqest).
- **Sliding Window Log**: Lưu **timestamp** (dấu thời gian) từng request . Giúp kiểm soát chạt chẽ các request hơn nhưng sẽ tốn bộ nhớ.
- **Silding Window Counter**: Kết hợp 2 loại trên.
- **Token Bucket**: Có 1 "bucket" chứa token, mỗi request tiêu 1 token. Token được refill theo tốc độ cố định (VD: 10 token/giây).Cho phép **brust**
- **Leaky Bucket**: Giống hàng đợi (queue) xử lý request với tốc độ cố định, dư thì tràn (drop). Làm mượt traffic (smoothing), không cho **burst**(Quá tải traffic).

### 4. Dùng gì để implement Rate Limit

**Redis**:

Ví dụ: Ví dụ với Fixed Window dùng `INCR` + `EXPIRE`:

```bash
INCR user:123:count
EXPIRE user:123:count 60   # chỉ set nếu key mới tạo
```

**Token Bucket / Sliding Window** thường viết bằng **Lua script** để đảm bảo atomic (tránh race condition giữa nhiều request đồng thời):

```bash
-- ví dụ đơn giản sliding window bằng sorted set
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < tonumber(ARGV[3]) then
    redis.call('ZADD', key, now, now)
    redis.call('EXPIRE', key, window)
    return 1
else
    return 0
end
```

**API Gateway/ Load Balancer level**:

- Nginx: limit_req_zone (leaky bucket), limit_conn_zone
- Kong, Envoy, AWS API Gateway, Cloudflare: có sẵn plugin rate limiting
- Ưu điểm: chặn request trước khi vào tới backend, giảm tải sớm

## XII. Metrics

### 1. Metrics là gì ?

**Metrics** là các số liệu định lượng được thu thập theo thời gian để đo lường trạng thái, hiệu năng, hoặc hành vi của một hệ thống.

- Khác với log (ghi lại sự kiện chi tiết, dạng text) hay trace (theo dõi đường đi của 1 request), metrics là dữ liệu dạng số, theo thời gian (time-series), và ta có thể tưởng tượng metric là 1 biểu đồ gồm số liệu hệ thống trên 1 khoảng thời gian (value, t)

### 2. Metrics đóng vai trò gì ?

- Monitoring & Alerting (giám sát & cảnh báo): Đây là vai trò cốt lõi nhất. Metrics được thu thập liên tục, khi vượt ngưỡng (threshold) thì trigger alert.
  - VD: error rate > 5% trong 5 phút → gửi cảnh báo cho team.

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_32.png)

- Observability (khả năng quan sát hệ thống): cho biết cái gì đang bất thường (VD: latency tăng cao)

- Giúp Dự đoán: Dựa vào xu hướng metrics theo thời gian để dự đoán khi nào cần scale thêm resource (CPU, RAM, node...).

### 3. Metrics xuất hiện ở đâu trong hệ thống

**Tầng hạ tầng (Infrastructure)**:

- CPU usage, RAM usage, disk I/O, network throughput
- K8s HPA: Số lượng pod/container đang chạy (Kubernetes)

**Tầng ứng dụng (Application)**:

- Request rate (requests/giây)
- Error rate (tỷ lệ lỗi %)
- Latency (thời gian phản hồi — p50/p95/p99)
- Throughput (số lượng transaction xử lý được)

**Tầng database**:

- Query latency, connection pool usage, số lượng slow query, cache hit ratio

**Tầng business**:

- Số lượng đơn hàng/phút, doanh thu real-time, tỷ lệ chuyển đổi (conversion rate), số user active

**Tầng dependency/downstream**:

- Latency khi gọi API bên thứ 3, tỷ lệ timeout, circuit breaker state

### 4. Các loại Metrics phổ biến

**Counter (bộ đếm)**: Giá trị chỉ tăng, không giảm (trừ khi reset).

- VD: tổng số request đã xử lý, tổng số lỗi.

**Gauge (đồng hồ đo)**: Giá trị có thể tăng/giảm tự do tại một thời điểm.

- VD: số lượng connection đang mở, RAM đang dùng, số job trong queue.

**Histogram**: Phân bố giá trị theo các "bucket" (khoảng).

- VD: phân bố thời gian phản hồi request — bao nhiêu % request dưới 100ms, bao nhiêu % từ 100–500ms...

**Summary / Percentile**: Tính toán các mốc percentile như p50, p95, p99 của latency — quan trọng hơn giá trị trung bình vì trung bình dễ bị "che" bởi outlier.

### 5. Các công cụ phổ biến để làm việc với Metrics

![Lab_System_Web](../01.Lab_default_web_system/images/Lab_Web_System_33.png)

Trình bày thành 1 chuỗi sự kiện cho ta dễ hình dung:

- **node exporter**: (blackbox exporter/ minio metris/ promtail) Là các agent để thu thập các dữ liệu của hệ thống(metrics thô: CPU, RAM, disk, connection hoặc log hệ thống)

- Các dữ liệu được node exporter expose(chạy như 1 webserver nhỏ) ra endpoint `HTTP /metrics` (dạng text, plain format)

- **Prometheus Server** chủ động scrape (kéo) trong config "cứ mỗi khoảng thời gian cố định (VD: 15s) nó sẽ tự gọi `HTTP GET` đến từng exporter để lấy dữ liệu mới nhất". 

- Rồi lưu các dữ liệu đó vào **Time-Series Database**(mỗi giá trị được gắn timestamp, tạo thành chuỗi thời gian)

- **Alertmanager** xử lý cảnh báo: Prometheus đánh giá các **alerting rule** liên tục. Nếu có vi phạm thì gửi tín hiệu đến **Alertmanager** để nó gom các nhóm cảnh báo(sao cho cảnh báo không lặp lại) và gửi đến kênh thông báo (Slack, Email, PagerDuty, Webhook...).

- **Grafana đọc & visualize**: Grafana kết nối tới Prometheus như 1 data source, gửi PromQL query, nhận kết quả, vẽ thành dashboard/biểu đồ cho người dùng xem.

- Loki: Giống như "Prometheus nhưng dành cho logs" — thiết kế theo triết lý tương tự (label-based indexing) nhưng thay vì lưu số liệu (metrics) thì nó lưu dòng log dạng text. Và thường đi kèm promtail

## XIII. CI/CD

### 1. CI/CD là gì?

**CI/CD** là "dây chuyền or quy trình lắp ráp tự động" cho phần mềm — thay vì con người phải build, test, deploy thủ công từng bước, hệ thống tự làm hết.

**(CI) — Tích hợp liên tục**:

- Developer commit/push code lên repository thường xuyên (nhiều lần/ngày).
- Mỗi lần push, hệ thống tự động build + chạy test để phát hiện lỗi sớm.
- Mục tiêu: tránh tình trạng "integration hell" — khi nhiều người merge code sau nhiều tuần thì xung đột (conflict) và lỗi chồng chất rất khó fix.

**Continuous Delivery (CD) — Chuyển giao liên tục**:

- Sau khi qua CI (build + test pass), code được tự động đóng gói(Containerization), chuẩn bị sẵn sàng để deploy.
- Vẫn cần con người bấm nút để deploy lên production (có bước approve thủ công).

**Continuous Deployment (CD) — Triển khai liên tục**:

- Giống Continuous Delivery, nhưng tự động deploy thẳng lên production mà không cần con người can thiệp, miễn là mọi bước kiểm tra đều pass.
- Đây là mức độ tự động hóa cao nhất.

### 2. Tác dụng của CI/CD

- **Tự động Build**: Compile code, đóng gói thành artifact (VD: file .jar, Docker image, bundle JS...).
- **Tự động Test**:

  - Unit test: test từng function/module riêng lẻ
  - Integration test: test sự tương tác giữa các module/service
  - E2E test (End-to-End): test toàn bộ luồng như user thật sử dụng
  - Nếu test fail → pipeline dừng lại, không cho merge/deploy tiếp, báo lỗi ngay cho dev.

- **Code Quality & Security Check**: Kiểm tra chất lượng code và bảo mật
- **Đóng gói & lưu trữ Artifact**: Build ra Docker image → push lên container registry (Docker Hub, AWS ECR, GitLab Registry...) để chuẩn bị deploy.
- **Deploy tự động**:Deploy lên các môi trường: `Dev` → `Staging` → `Production`, thường theo chiến lược:

- Rolling deployment: thay thế dần từng instance cũ bằng instance mới
- Blue-Green deployment: chạy song song 2 môi trường (Blue = cũ, Green = mới), chuyển traffic sang Green khi ổn định
- Canary deployment: release cho 1 % nhỏ user trước, theo dõi ổn thì tăng dần %

- **Rollback tự động**: Nếu deploy mới gây lỗi (phát hiện qua health check/metrics), một số pipeline tự động rollback về version trước đó.

- **Thông báo về pipeline**: Gửi kết quả pipeline (thành công/thất bại) qua Slack, Email, Teams... cho team biết ngay.

### 3. Cơ chế hoạt động CI/CD pipeline

```text
[Developer viết code]
        ↓ git push
[Source Control - Git repository (GitHub/GitLab/Bitbucket)]
        ↓ (trigger tự động khi có push/merge request)
┌─────────────────────────────────────────────────┐
│              CI/CD PIPELINE                     │ 
│                                                 │
│  1. Checkout code                               │
│  2. Install dependencies                        │
│  3. Build (compile code, build Docker image)    │
│  4. Run tests (unit test, integration test)     │
│  5. Static code analysis / Lint / Security scan │ 
│  6. Push artifact (Docker image → registry)     │
│  7. Deploy to Staging/Dev environment           │
│  8. Run E2E test / smoke test trên staging      │
│  9. (Approval - nếu là Continuous Delivery)     │
│  10. Deploy to Production                       │
│                                                 │
└─────────────────────────────────────────────────┘
        ↓
[Production - hệ thống đang chạy thật]
        ↓
[Monitoring/Alerting - Prometheus, Grafana theo dõi sau khi deploy]
```

## XIV. Ansible

### 1. Ansible là gì ?

Ansible thay thế công việc bạn đó SSH vào từng server để chạy lệnh cài đặt, config, restart service thủ công .Ansible cho phép bạn viết 1 file mô tả "trạng thái mong muốn" rồi chạy 1 lệnh, nó sẽ tự động thực hiện trên hàng trăm/hàng nghìn server cùng lúc.

Ansible chỉ cần:

- SSH (Linux) hoặc WinRM (Windows) đã có sẵn trên server đích.
- Python đã cài trên server đích (hầu hết Linux đều có sẵn).

### 2.Công dụng Ansible

- Nó na ná Với file DockerCompose trong Docker để quản lí 1 Instances Container nhưng ở đây phạm vi của nó là Ansible để quản lí các VM instances chạy trong server vật lí thật
- Nó giúp rút gọn các bước triển khai trên server hạ vầng vật lí như:

  - Deploy cụm OpenStack kết hợp với Kolla Ansible
  - Deploy cụm K8s nhanh

### 3. Các khái niệm chính trong Ansible

|Khái niệm|Ý nghĩa|
|---------|-------|
|Inventory|Danh sách các server (host) mà Ansible sẽ quản lý, có thể nhóm theo tag (VD: webservers, dbservers)|
|Playbook|File YAML mô tả các tác vụ (task) cần thực hiện trên host nào|
|Task|1 hành động cụ thể (VD: cài package, copy file, restart service)|
|Module|Đơn vị thực thi task (VD: module `apt`, `yum`, `copy`, `service`,`docker_container`...) - Ansible có hàng nghìn module built-in|
|Role|Gói nhiều task/template/variable lại thành 1 đơn vị tái sử dụng được (VD: role "nginx", role "mysql")|
|Handler|Task chỉ chạy khi được trigger bởi task khác (VD: restart service chỉ khi file config bị thay đổi)|
|Variable|Giá trị có thể tùy biến theo môi trường (dev/staging/prod)|
|Playbook execution (Ansible Control Node)|Máy chạy lệnh ansible-playbook, nơi cài Ansible, kết nối SSH đến các máy đích|

### 4. Một số lệnh Ansible cơ bản

#### a. Kiểm tra kết nối & thông tin cơ bản

```bash
# Ping tất cả host trong inventory
ansible all -m ping

# Ping theo group cụ thể
ansible webservers -m ping

# Xem inventory hiện tại
ansible-inventory --list
ansible-inventory --graph

# Kiểm tra syntax của playbook trước khi chạy
ansible-playbook site.yml --syntax-check
```

#### b. Chạy Ad-hoc command (lệnh nhanh, không cần viết playbook)

```bash
# Chạy lệnh shell trên tất cả server
ansible all -m shell -a "uptime"

# Chạy lệnh command (an toàn hơn shell, không qua shell interpreter)
ansible all -m command -a "df -h"

# Copy file đến nhiều server cùng lúc
ansible webservers -m copy -a "src=./app.conf dest=/etc/app.conf"

# Cài package
ansible webservers -m apt -a "name=nginx state=present" --become

# Restart service
ansible webservers -m service -a "name=nginx state=restarted" --become

# Kiểm tra disk usage, sau đó lọc
ansible all -m shell -a "df -h /" 

# Tạo user
ansible all -m user -a "name=deploy state=present" --become

# Reboot server
ansible all -m reboot --become
```

#### c. Chạy Playbook

```bash
# Chạy playbook cơ bản
ansible-playbook site.yml

# Chỉ định inventory file cụ thể
ansible-playbook -i inventory.ini site.yml

# Chạy với quyền sudo (nếu chưa set sẵn trong playbook)
ansible-playbook site.yml --become

# Chạy thử (dry-run) — xem sẽ thay đổi gì mà KHÔNG áp dụng thật
ansible-playbook site.yml --check

# Chạy dry-run + hiển thị diff chi tiết (file nào đổi, đổi gì)
ansible-playbook site.yml --check --diff

# Chỉ chạy trên 1 nhóm/host cụ thể
ansible-playbook site.yml --limit webservers
ansible-playbook site.yml --limit "web1,web2"

# Chỉ chạy các task có tag cụ thể
ansible-playbook site.yml --tags "install,config"

# Bỏ qua các task có tag cụ thể
ansible-playbook site.yml --skip-tags "restart"

# Tăng độ chi tiết log để debug (thêm nhiều -v hơn = log chi tiết hơn)
ansible-playbook site.yml -v
ansible-playbook site.yml -vvv

# Truyền biến trực tiếp qua command line
ansible-playbook site.yml --extra-vars "env=production version=1.2.3"

# Chạy lại chỉ những host bị fail ở lần chạy trước
ansible-playbook site.yml --limit @site.retry
```

#### d. Ansible Vault (quản lý secret)

```bash
# Tạo file secret mới đã mã hóa
ansible-vault create secrets.yml

# Mã hóa file có sẵn
ansible-vault encrypt secrets.yml

# Giải mã file (cẩn thận khi dùng)
ansible-vault decrypt secrets.yml

# Sửa file đã mã hóa
ansible-vault edit secrets.yml

# Xem nội dung file đã mã hóa
ansible-vault view secrets.yml

# Đổi password mã hóa
ansible-vault rekey secrets.yml

# Chạy playbook có dùng vault, nhập password khi chạy
ansible-playbook site.yml --ask-vault-pass

# Chạy playbook, đọc password vault từ file
ansible-playbook site.yml --vault-password-file ~/.vault_pass.txt
```

#### c. Quản lý Role & Collection (Ansible Galaxy)

```bash
# Cài role từ Galaxy
ansible-galaxy install geerlingguy.nginx

# Cài từ file requirements.yml (nhiều role/collection cùng lúc)
ansible-galaxy install -r requirements.yml

# Tạo khung role mới
ansible-galaxy init roles/my_new_role

# Liệt kê role đã cài
ansible-galaxy list

# Cài collection (VD: community.docker, community.general)
ansible-galaxy collection install community.docker
```

# Xem tất cả facts (thông tin hệ thống) của 1 host

ansible webserver1 -m setup -a "filter=ansible_default_ipv4"
